# Frontend Internationalization (zh-CN + English) Design

Date: 2026-07-09

## Summary

Re-introduce multi-language support to the React frontend: Simplified Chinese (current) plus English. The project previously shipped Vue + `vue-i18n`; that stack was removed during the Vue→React rebuild (commit `0dcc294 refactor(web): 移除 vue-i18n 多语言支持，仅保留中文`), leaving a Chinese-only string catalog at `web/src/locales/` with a tiny homegrown `t(key, params)` helper. This design extends that helper into a real two-language system: a Zustand locale store drives language selection, `t()` resolves the active language's messages, a `useTranslation()` hook makes UI reactive to switches, and all remaining hardcoded Chinese strings are migrated to translation keys so English is fully covered. The backend already returns English responses and English logs, so it is untouched.

## Decisions

| Decision | Choice | Rationale |
|---|---|---|
| i18n mechanism | Extend the existing homegrown `t()` — no new dependency | A heavy i18n library was just deliberately removed; the app's strings are mostly labels/buttons with no pluralization/gender needs; keeps bundle small |
| Reactivity mechanism | Zustand locale store + `useTranslation()` hook | Matches the existing `auth`/`panel` Zustand stores; minimal boilerplate; `t()` stays callable from non-component code via `getState()` |
| Language detection | Auto-detect `navigator.language`, manual override persisted in `localStorage`, default `zh-CN` | Single-user homelab panel — friendly first run, but lets the user pin a preference |
| Localization scope | Text **and** date/number/MUI-component locale | Consistent experience; honors user preference for English date formatting |
| Switcher placement | New `LanguageSection` inside **其他设置 (Misc Settings)** tab | Co-located with other personal preferences (password, backup/restore); avoids cluttering the home screen |
| Translation file format | Inline ESM-imported JSON, mirrored structure | Files are tiny; consistent with current `import zhCN from './zh-CN.json'`; no lazy-loading complexity |
| Pluralization / gender | Not supported (YAGNI) | App has no strings that need it |
| Backend | No change | Client-facing responses and operation logs are already English |

## Architecture

### Core modules

1. **Locale store** — new file `web/src/store/locale.ts` (Zustand):
   ```ts
   type Lang = 'zh-CN' | 'en'
   interface LocaleState {
       lang: Lang
       setLang: (lang: Lang) => void
   }
   ```
   - State initializer reads `localStorage['homelab-lang']`; if absent, matches `navigator.language` (any `zh*` → `zh-CN`, otherwise `en`); falls back to `zh-CN`.
   - `setLang(lang)` updates state and writes `localStorage['homelab-lang']`.
   - A standalone `initLocale()` (or the store's initial state) resolves the starting language **synchronously at module load** so the very first paint uses the correct language.

2. **Translation resolver** — extended `web/src/locales/index.ts`:
   - Imports both `zh-CN.json` (existing) and the new `en.json` into a `{ 'zh-CN': zhCN, en: en }` map.
   - `t(key, params)`: reads `useLocaleStore.getState().lang`, resolves the dotted key against that language's messages, interpolates `{param}` placeholders, and **falls back to the key itself** when missing (so an untranslated key is visible, never crashes).
   - `useTranslation()` hook: subscribes to `lang` (`useLocaleStore(s => s.lang)`) and returns `{ t, lang }`. Subscribing is what triggers re-render on language change; `t` then reads the newly active messages. Existing bare `t()` imports migrate to `const { t } = useTranslation()` inside components; non-component code (stores, utils, API fallbacks) keeps using the plain `t()`.
   - `LANGUAGES` registry: `[{ code: 'zh-CN', label: '中文' }, { code: 'en', label: 'English' }]` for the switcher.
   - `localeTag(lang)` helper → `'zh-CN'` / `'en-US'` for `Intl`/`toLocaleString` calls.

3. **Reactive MUI theme** — `web/src/theme/theme.ts`:
   - Export `buildTheme(lang)` instead of a static singleton; it calls `createTheme(base, muiLocale)` where `muiLocale` comes from `@mui/material/locale` for the active language (exact import path verified against the installed MUI version during implementation).
   - `main.tsx` wraps the tree in a small `<ThemedRoot>` that reads `lang` from the store and memoizes `buildTheme(lang)`, so MUI components re-localize on switch. (Current impact is small — the app uses no DatePicker/Calendar/DataGrid — but this honors "MUI locale follows" and future-proofs it.)

### Translation file organization

Keys are namespaced by feature, mirroring the source layout:

```jsonc
{
  "common": { "appName": "...", "add": "...", "cancel": "...", ... },
  "login":  { "loginButton": "...", "welcomeMessage": "...", ... },
  "home":   { "addGroup": "...", "editMode": "...", ... },
  "settings": { "tabPage": "...", "tabMisc": "...", "language": "...", ... },
  "files":  { "upload": "...", ... },
  "mcp":    { "...": "..." },
  "about":  { "...": "..." },
  "errors": { "serverError": "...", "unauthorized": "...", ... }
}
```

`en.json` mirrors this structure 1:1. The existing `zh-CN.json` (~20 keys under `common`/`login`/`iconItem`) is preserved and extended.

## Language Detection Policy

```
On app start (synchronous, module load):
  stored = localStorage['homelab-lang']
  if stored in {zh-CN, en}         → lang = stored
  else if navigator.language startsWith 'zh' → lang = 'zh-CN'
  else                              → lang = 'en'   // anything non-zh → English
  (final fallback if navigator unavailable: 'zh-CN')

On manual switch:
  setLang(next) → state.lang = next; localStorage['homelab-lang'] = next
```

## Localization Scope

| Surface | Behavior |
|---|---|
| All UI text | Resolved via `t()`; English fully covered |
| `document.documentElement.lang` | Set to active `lang` on init and on switch |
| Dates / numbers (`MCPSettingsPanel` `toLocaleString`) | Uses `localeTag(lang)` instead of hardcoded `'zh-CN'` |
| MUI component locale | Theme rebuilt with `@mui/material/locale` for active lang |
| `moment` | `moment.locale(lang)` set on init/switch (the `Clock` uses fixed `HH:mm`, so it is unaffected in practice — kept for consistency) |

## UI Design

### Language switcher

Inside **其他设置 (Misc Settings)** (`MiscSettingsPanel`, `web/src/components/apps/SettingsPanels.tsx`), add a `LanguageSection` at the top (above `ChangePasswordSection`):

- A MUI `Select` populated from the `LANGUAGES` registry, showing the active language.
- On change → `setLang(code)`; the whole app re-renders immediately in the new language (no reload).
- A short helper line under the field (translated) explaining the choice persists.

All settings **tab labels** (`AppStarter.tsx`: 页面设置 / 应用设置 / MCP设置 / 其他设置 / 关于) and dialog titles are themselves routed through `t()`.

## Data Flow

```
App start:
  locale store initializer → resolves lang (localStorage → navigator → default 'zh-CN')
  → ThemedRoot builds theme(lang) → ThemeProvider renders localized MUI
  → document.documentElement.lang = lang; moment.locale(lang)
  → AppRouter renders; components call useTranslation() → t() resolves active messages

Language switch:
  User picks a language in LanguageSection → setLang(next)
  → localStorage written; store.lang updates
  → useTranslation() subscribers re-render → t() returns next language's text
  → ThemedRoot re-builds theme(next); html lang + moment locale updated
```

### Migration scope (text → keys)

Full coverage is required so English is never half-baked. Work proceeds in two waves:

1. **Existing `t()` call sites (~13 files)** — switch from bare `import { t }` to `const { t } = useTranslation()` inside components, keeping plain `t()` only for non-component modules. Files include `Login.tsx`, `FileManagerPanel.tsx`, `ImageUploadButton.tsx`, `EditItemDialog.tsx`, `ImportExportPanel.tsx`, `GroupManager.tsx`, `SettingsPanels.tsx`, `useHomeActions.ts`, `HomeGroup.tsx`, `useHomeSort.ts`, `HomeContextMenu.tsx`, and related hooks.

2. **Hardcoded-string files (~32 files)** — extract every user-visible Chinese string into a namespaced key and provide the English value. Representative areas:
   - **Settings**: `SettingsPanels.tsx` (网站图标 / 远程图标 / 自动, dialog titles), `AppStarter.tsx` tab names, password-change section.
   - **Common**: `ConfirmProvider.tsx` (`确认操作` / `取消` / `确认` defaults), `EditItemDialog.tsx`, `ImageUploadButton.tsx`, `ItemIcon.tsx`, `AppIcon.tsx`, `ColorSwatchPicker.tsx`, `ColorModeSelector.tsx`, `AuthBootstrap.tsx`.
   - **Pages / home**: `Home.tsx`, `HomeHeader.tsx`, `HomeFloatingActions.tsx`, `HomeGroup.tsx`, `useHomeData.ts`, `NotFound.tsx`, `ServerError.tsx`, `SearchBox.tsx`.
   - **Files**: `FileManagerPanel.tsx`, `FilePickerDialog.tsx`.
   - **Errors / API fallbacks**: `api/session.ts`, `api/apiResult.ts`, `api/stubs.ts`, `api/mcp.ts`, `store/auth.ts`, `store/panel.ts`, `hooks/useApiAction.ts`, `utils/clipboard.ts` — server-error / fallback messages routed through `t()` under the `errors.*` namespace.

   The exact per-file key mapping is enumerated in the implementation plan; this spec fixes the **scope** (every user-visible string migrates) and the **namespace scheme**.

## Backend Changes

None. Client-facing responses (`internal/handlers`) and operation logs (`internal/logging`) are already English-only; the only Chinese in `internal/` is a code comment. The MCP DTO / panel service layer is unaffected.

## Edge Cases

| Scenario | Behavior |
|---|---|
| Missing key in active language | `t()` returns the key string itself (visible, never crashes); prevents a partial `en.json` from breaking the UI |
| `en.json` key absent but present in `zh-CN.json` | Same key-fallback; surfaces untranslated keys so they are easy to spot and fix |
| `localStorage` disabled / throws | Detection falls through to `navigator.language` → default `zh-CN`; switch silently keeps working in-memory for the session |
| `navigator.language` unset (SSR/prerender) | Default `zh-CN` |
| User switches language mid-edit in a dialog | Dialog text re-renders; form state is component-local and unaffected |
| Existing tests asserting Chinese strings | Default language stays `zh-CN`, so current assertions still pass; tests that pin a language use the store's `setLang` |

## Non-Goals

- Pluralization, gender, ICU MessageFormat.
- Backend response / log translation.
- Right-to-left languages or additional locales beyond `zh-CN` / `en` (the registry is extensible, but no others ship now).
- Lazy-loading of translation bundles (files are tiny; inline import).
- Translating code comments, the MCP tool descriptions, or Swagger docs.
